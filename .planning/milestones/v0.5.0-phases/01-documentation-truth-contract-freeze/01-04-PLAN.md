## This is a verify-then-extend task, not a from-scratch one

RESEARCH.md Pitfall 4 and VALIDATION.md's Wave 0 both record that success criterion 2 is
**mostly already satisfied**. `tests/Core/SpatialMathTests.cpp` already carries four
`outputLimiter` test cases at lines 66-98, and the parameterised loop at lines 73-81 already
spans values below the ceiling, exactly at the ceiling, and above it:
`{ -5.0f, -1.2589f, -0.5f, 0.0f, 0.5f, 1.2589f, 2.0f, 5.0f, 100.0f }`.

The gap is **legibility, not coverage**. A single loop over nine values does not self-document
"this covers at, below, and above the ceiling" for someone auditing the criterion later. Plan the
decision (verify, then split for auditability), not a test rewrite. Scoping this as "add the
missing boundary tests" over-scopes a near-complete item.

## Assumption-delta assessment (advisory, non-blocking)

The assumption-delta detector fired once on the term `selectable`, against the snippet
*"existing users. A selectable hard-clamp mode is deferred to v2 as LIMIT-01."*

**Assessment: agreed, no action.** The signal is a hit on a **deferred v2 candidate**, not on a
transition this phase performs. Phase 1 freezes the single shipped transfer function and defers
the selectable-mode generalisation to v2 as LIMIT-01.

Freezing the docblock now does **not** foreclose LIMIT-01. The docblock describes what
`outputLimiter()` currently does; it is not a promise that only one mode will ever exist. A v2
author adds the mode **alongside** — a new entry point, or a parameter defaulting to the tanh
curve — which is additive and does not break DR-2, exactly as REQUIREMENTS.md already records.
One line of guidance for that author: add alongside, do not promote this docblock into a
mode-agnostic abstraction now. Generalising a contract before a second implementation exists
would trade a true, specific statement for a vaguer one, which is the opposite of this phase's
goal. This is not a scope expansion in either direction.
