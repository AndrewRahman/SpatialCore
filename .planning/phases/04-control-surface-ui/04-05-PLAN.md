## Ground rules for this plan

- **The user is not a programmer.** Claude runs every build and test; nothing here asks the user anything.
- **Diff base:** `BASE` = the commit HEAD pointed at when this plan started (record it in the SUMMARY).
- **One plan at a time.** Phase 4 runs serially; this plan starts from the tree Plan 04-04 committed.
- **Build trees** as Plan 04-01 configured them (Debug `build/`, Release `build-release/`); if a
  `CMakeCache.txt` is missing, configure with Plan 04-01's ground-rule block.
- **From this plan on there are two Catch2 executables.** Every gate builds all targets
  (`cmake --build build -j8`, `cmake --build build-release -j8`) before `ctest`; building only
  `SpatialCoreTests` and then running `ctest` would fail on a `SpatialCoreUITests_NOT_BUILT` placeholder
  (RESEARCH Pitfall 7). Debug binaries: `./build/tests/SpatialCoreTests`, `./build/tests/SpatialCoreUITests`.
- **Catch2 v3** exits non-zero on a failed assertion and when a filter matches nothing ("No test cases matched").
- **Expected Debug noise:** the `juce_LeakedObjectDetector` assertion at exit; libmysofa lines starting with `/Users/`.
- **Headless UI rules (RESEARCH Pattern 1, Pitfalls 9-11):** components are constructed without a window
  and painted into a `juce::Image`; no message-loop pumping is needed for components, listeners or
  painting (so `SpatialCoreUITests` does not get `JUCE_MODAL_LOOPS_PERMITTED`); `Desktop::getMainMouseSource()`
  and painting need the JUCE GUI initialiser, which the listener provides. Keep test code portable: CI
  compiles every target on Linux (it does not run them), so no macOS-only API in tests.
- **Style:** as the existing tests; shared UI helpers in `namespace spatialcore::test`.
- **Threads:** UI code is message-thread code; nothing here touches the audio path (DR-1).

## Research numbers (04-RESEARCH.md "Synthesized drag", "Pixel numbers")

Geometry (`SpatialMapComponent.cpp:78-84`): radius `min (w, h) * 0.45`, `x = cx - sin (az) * d * radius`,
`y = cy - cos (az) * d * radius`; positive azimuth is the left of the screen and of the sound. A 400x400
map with object 0 at (az 0, el 30, d 0.5): mouse-down on `getObjectScreenPos (0)`, drag to
`(200 - 0.8 * 180, 200)` reports az 90.000, d 0.800, elevation still 30.00. Objects at az +90 el +80 and
az -90 el -80 (d 0.5): pixel at (object x + 4, object y) is `ffed5e5e` (object colour 0, fill alpha 1.0)
above and `ff5c4027` below (fill alpha 0.3). Rings are drawn at r = 0.25, 0.5, 0.75, 1.0 of the radius
(0.7 px stroke); ring labels sit at 30 and 210 degrees screen angle. Dragging to the exact centre gives
`atan2 (-0, -0)`, so only distance is asserted there (RESEARCH A4).
